# RewardKit: smallest setup

Use standalone RewardKit when useful for grading saved outputs, files, and traces from agentic evaluations or simulated interactions. Harbor is optional execution infrastructure. Official [RewardKit quick start](https://docs.harborframework.com/core-concepts/rewardkit/quick-start), [judge configuration](https://docs.harborframework.com/core-concepts/rewardkit/judge-criteria), and [Harbor verifier tutorial](https://docs.harborframework.com/tutorials/create-a-verifier-with-rewardkit) were checked 2026-09-28.

Install `uv tool install harbor-rewardkit` when setup is requested, then inspect `rewardkit --help`. The locally verified release is 0.2.0; record and pin the actual release in each experiment. Do not install all document extras or a container runtime for plain text. Follow the main skill's subscription-first routing: use the local Claude or Codex CLI when compatible. If the installed framework requires an API, use a small supported adapter or a simpler runner; do not silently choose OpenRouter or another paid endpoint. For explicitly authorized API routes, use the approved provider environment; never put keys in files or command arguments. Check credential presence without printing values.

Run with explicit local paths: `rewardkit /absolute/tests --workspace /absolute/saved-answer --output /absolute/run/reward.json`. Defaults target Harbor's `/app` and `/logs`, which are inappropriate host paths. Save both reward.json and reward-details.json; inspect per-criterion errors even when the process exits successfully. Missing/errored judgments are not valid zero scores.

For image-grounded tasks, pass the actual image files to a vision-capable judge and verify successful file loading; filenames and summaries are insufficient. Keep trusted references outside subject-writable state. RewardKit scans subdirectories as scoring groups: keep reference assets outside the selected criteria directory rather than mixing arbitrary asset directories into its discovery root. In Harbor, a dedicated verifier Dockerfile must bake in its tests and references; explicitly declare the answer artifacts to transfer.

RewardKit 0.2.0 silently substitutes a “file too large” marker for files over 1 MB, including images. Check the installed loader and inspect assembled content before paid grading. If needed, retain original images and make legible, size-bounded derivatives; verify every expected image is actually included. Treat grades produced with omitted task evidence as invalid, not merely low confidence. The installed 0.2.0 aggregation names use underscores such as `all_pass`; newer docs may show hyphens. Validate against the installed parser.

Verify model routing separately from authentication. A model advertised by the desktop app or an injected local cache may still be rejected by a CLI login endpoint. Preserve the requested evaluator identity; when using another configured provider for that same model, record its full routing string, credentials mechanism and billing path. Do not silently replace the judge model to make a run succeed.

Use Python `@criterion` functions for deterministic or existing scoring code, and TOML judges for newly designed subjective rubrics. Keep authoritative inputs outside editable subject state. Built-in weighted means can change benchmark meaning: preserve coverage gates, penalties, caps, and the main composite explicitly when replicating a scorer. Test parity against direct scorer calls on identical saved outputs and judge data; old published scores may reflect an older rubric.

Separate delivery checks from subjective quality. Missing, empty, malformed or invalid file outputs can fail deterministically without a judge call. A missing credential, provider failure, timeout or malformed judge response is an evaluator error: retain diagnostics and withhold a normal reward rather than reporting it as a poor answer. Inspect `reward-details.json` for these conditions even when a numeric reward was emitted. Make the aggregation rule explicit and retain criterion-level results; successful delivery must not conceal a critical quality failure.

Use a fresh output directory per attempt. Capture raw returned judge content and provider usage before an adapter discards them; check that asynchronous logging actually flushed. Prefer supported logging hooks, with a small transparent response recorder only when needed. Record instrumentation gaps rather than rerunning a paid grade just to recover accounting data. Keep scoring unchanged when adding instrumentation.

Use the evaluator declared in the main skill's pre-run plan, preserving any explicit user selection. Choose reasonable defaults and proceed without confirmation for subscription CLI calibration and grading; API spending requires explicit confirmation unless already authorized. Check the installed schema and actual provider routing rather than assuming an SDK uses the subscription. Test one tiny known-good/bad pair before a suite. Cross-provider judge choice reduces one potential bias but does not validate the rubric by itself. Preserve full subject outputs before any judge call, raw judge results, criterion reasoning, grading usage, cost, and elapsed time (mark unavailable values explicitly), and human agreement as unreviewed.

Programmatic and judge criteria run concurrently by default. Make criteria read-only or isolate scratch state; do not assume Linux overlayfs isolation works on macOS. For mutable tools or service state use Harbor's supported environment/isolation features instead.

Generation, RewardKit grading, and the inspection report are separate stages. Regrade saved outputs without buying new subject responses. Distinguish replay of stored judgments, fresh judgments on stored answers, and new end-to-end trials in the report. Do not claim a live model or native RewardKit judge was exercised by a cached-score adapter.
