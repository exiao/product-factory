# Verify feature

Verification is runtime observation. Read the diff, identify the user-facing surface reached by the changed code, run the app or service, drive the smallest path that executes the change, and capture the result. Tests, typechecks, imports, and code reading can support a report but do not substitute for reaching the real surface.

Start by stating the commit/diff scope and whether the change is visual, behavioral, backend, CLI, or configuration. Map it to a surface: terminal for CLI/TUI, an HTTP request for an API, a real browser capture for web UI, the native simulator for native UI, or the running agent for prompt/config changes. Use the actual application route and its real host, state, and handlers by default. A component preview is supplemental evidence. Use a throwaway harness only after observing a concrete blocker to reaching the application or affected branch, such as a failed build, unavailable authentication, or unavailable native store eligibility. Record the blocker and the application paths the harness bypasses; label its footage as a harness and limit its verdict to the exercised component behavior. A harness pass does not establish an integrated feature pass.

For a data-dependent claim, run with real source data through the production data path and observe the final user-facing result. Record the source, as-of time, relevant input values and units, and the returned payload so the content can be checked against what actually happened. Use a safe account, device, or read-only target when personal or external data is involved. A fixture, hand-written example, or mocked API response can test rendering or an error branch, but cannot prove live data correctness or an end-to-end flow. If a harness must ingest real data into an isolated store, identify which production ingestion steps it bypasses and limit the verdict to the path exercised. If the real source is unavailable, report BLOCKED or INCONCLUSIVE for the data-dependent claim; do not promote a mock-backed capture to PASS.

For a substantial UI branch, map the changed user journeys before choosing test cases: entry, actions, validation or error branches, side effects, and the true end state after any follow-up navigation. Derive scenarios from those journeys so a successful intermediate action does not hide a wrong destination. A short outline suffices for a simple flow; draw a diagram only when its branching is easier to understand visually. Keep small, single-screen changes on the smallest relevant path.

Drive the changed behavior, including the claimed interaction and its resulting state. When both a returned result and persisted state are claimed, verify each separately. For destructive, publishing, sending, or external-write paths, use a dry-run or safe target; otherwise verify surrounding behavior and clearly mark the live path untested. For visual changes, capture matched before/after states from the same route, viewport, auth state, data, and capture method. A new surface or a non-visual change may use an after-only capture when that exception is stated.

**Always deliver visual evidence.** Record a short video of the observed runtime surface whenever recording is available. For browser flows, prefer `shot-scraper video` when an installed version supports it; use Playwright video as a fallback or when existing test automation already drives the actual journey. Use the surface's equivalent recorder for native apps or terminals. Capture the action and its resulting state in one continuous run. Make the saved clip reviewable: begin on the meaningful starting state, show the action at a pace a person can follow, and leave the resulting state visible long enough to read. Inspect the opening, action, and ending in the actual exported file before sharing it, and inspect the entire final clip for unrelated/private content and visible errors. If setup or loading dominates the clip, record again from a ready state or trim only the irrelevant lead-in; keep the untouched original recording, save any trimmed or annotated version as a separate derivative, and disclose any speed or time changes; if the delay is part of the changed user experience, keep it and report it. Never use a mostly blank clip or one that shows the feature only at the end as passing evidence. Use a screenshot only when video capture is unavailable. Attach or embed the video or screenshot in the final response. The artifact must show the actual observed runtime surface, including CLI, API, backend, and configuration results where applicable, not a recreated or illustrative state. Save a local copy when the capture tool supports it, and label mocks, dry runs, and harnesses on the artifact or next to it. If capture is unavailable, report BLOCKED or INCONCLUSIVE rather than claiming PASS without visual evidence.

For browser capture, read [browser video](references/browser-video.md). `shot-scraper video` records real browser interactions from YAML storyboards, supports cursor and click visualization, and can convert WebM to MP4. Check the installed command before choosing a fallback; do not infer capabilities from the tool name or older guidance. `shot-scraper` and the in-app browser also support still screenshots. Do not install tools or publish evidence automatically. New-tab links require driving the new tab or window, not treating a same-tab timeout as a product failure.

Deliver actual-app footage as the primary verification artifact whenever that path was reachable. Report verdicts per branch: for example, web dismissal PASS and native trial checkout BLOCKED. If only a harness reached the new branch, do not present it as the actual app or report the whole feature PASS. A real-app recording of a different branch does not close that gap. Use fixed viewport and video dimensions throughout a clip; record another clip for a different breakpoint so resizing does not leave blank or padded frames.

Probe at least one realistic edge case or failure path. Record method, exact route/command, evidence paths, what was not tested, and a verdict of PASS, FAIL, BLOCKED, or INCONCLUSIVE. When a pass could arise from a model, provider, or service fallback or cache, identify the path that produced the result, include a run ID when available, and limit the verdict to that path. Preserve the user's requested review/fix/publish scope: verification does not authorize changing code, pushing, or publishing.

For a QA pass large enough to span sessions, create a resumable scenario record before execution and update it as each scenario finishes. Track pending, passed, fixed, or blocked status, the evidence, and the remaining decision or action. Reuse a repository report or task artifact when one exists; a short one-off verification needs no new file. Follow [runtime evidence](references/runtime-evidence.md) for resume rules.

When a consequential or recurring failure can be replayed, preserve its minimal request, relevant starting state, observed failure, verifier, and reset instructions using the [failure-to-eval handoff](references/failure-to-eval.md). Reuse existing fixtures; ordinary one-off verification does not require a new harness or case library. Keep expected answers and failure diagnoses out of the executor's inputs.

For a comparative improvement claim, run baseline and candidate with equivalent starting state, tool access, and evaluator configuration; retain both outcomes and material time/cost differences. An after-only check proves the observed behavior, not improvement over the baseline. A replay or simulation supports only the behavior it exercises; retain real-surface verification for live claims.

Read [references/runtime-evidence.md](references/runtime-evidence.md) for the report and before/after rules, and [references/inert-feature-probe.md](references/inert-feature-probe.md) when a change may be wired into no real caller.
